Machines

{{template "team-machines" .}}
Add a machine

An admin creates the machine and stores the key it prints as the job's or app's secret ESEC_VAULT_MACHINE_KEY:

{{template "cmd" (printf "esec vault machine create deploy --env prod --github-repo %s --github-ref refs/heads/main" .Project)}}

The job then runs its command with the keys in its environment:

{{template "cmd" "esec-vault machine run -- esec run prod -- ./deploy.sh"}}

With --github-repo, the server hands the sealed keys only to GitHub Actions jobs of that repository (and ref) that prove it with an OIDC token, so a leaked secret alone is not enough. For many machines, use a group.

Groups

{{template "team-groups" .}}
Let a group of people or machines read this project {{template "cmd" (printf "esec vault access grant acme/backend --project %s --env dev,staging" .Project)}}

The group's admins agree first (they choose the projects it reads), then an admin of the project grants environments: one command does both when you administer both. The group's page lets you tick environments too.

Rename or transfer to another tenant

A device makes an atomic move: a new signed project with the same keys, and this one archived pointing there. Cross-tenant transfers require source-project admin rights and ownership of both tenants; source people, groups and machines are not copied. For a different receiving owner: esec vault project transfer SOURCE --to DEST --recipient LOGIN. Former readers may still hold keys: rotate them and re-encrypt files to revoke access. Then change project in the repository's esec.toml.
